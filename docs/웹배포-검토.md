# 웹에 배포해서 쓰면 어떨까? — 검토 결과

> 2026-08-01 작성. "친구가 URL만 치면 되게 웹에 올려두는 게 더 편하지 않나?"에 대한 답.
> ⚠️ 법률 전문가가 쓴 글이 아니다. 판단 재료로만 쓰고, 실제로 공개 서비스를 할 거면 변호사에게 확인할 것.

## 결론 먼저

**하지 마세요. 편해지지도 않고, 법적 위험만 완전히 다른 차원으로 올라갑니다.**

세 가지 이유인데, 사실 **1번만으로도 이미 결론이 납니다.**

1. **기술적으로 오히려 더 안 됨** — 클라우드 서버 IP는 유튜브·틱톡이 상시 차단한다
2. **법적으로 완전히 다른 영역** — "내 컴퓨터에서 내가 쓰는 도구"와 "남에게 제공하는 서비스"는 하늘과 땅 차이
3. **실제로 더 불편함** — 다운로드를 두 번 하게 되고, 지금 있는 기능 절반이 못 쓰게 됨

---

## 1. 기술적으로 오히려 더 안 된다 (이게 결정타)

우리가 이번 주에 계속 싸운 그 에러를 기억할 것:

```
Sign in to confirm you're not a bot
Unable to extract universal data for rehydration
```

이건 **봇 차단**이다. 그리고 유튜브·틱톡의 봇 차단은 **어느 IP에서 왔는지를 가장 크게 본다.**

| | 집 인터넷 (지금) | 클라우드 서버 (AWS·Vercel 등) |
|---|---|---|
| IP 종류 | 가정용 (KT/SKT 등) | 데이터센터 |
| 봇 취급 | 거의 안 함 | **기본적으로 의심** |
| 차단 빈도 | 가끔 (재시도로 해결됨) | **상시** |

yt-dlp 커뮤니티에서 데이터센터 IP는 봇 탐지에 상습적으로 걸리는 것으로 알려져 있고, 권장 해결책이 아예 **"데이터센터/VPN IP를 쓰지 말고 일반 인터넷 회선을 쓰라"**는 것이다.

우회하려면 주거용 프록시(residential proxy)를 돈 주고 사야 하는데, 그건 비용도 비용이고 **"차단을 우회하려고 돈 주고 위장 IP를 샀다"**는 사실 자체가 나중에 문제가 될 때 최악의 정황이 된다.

> **요약: 지금은 가끔 재시도하면 되는 걸, 웹에 올리면 아예 안 되는 상태가 된다.**

## 2. 법적으로는 완전히 다른 영역이 된다

여기가 핵심이다. **무엇을 다운로드하느냐가 아니라, 누가 누구에게 제공하느냐가 법적으로 결정적이다.**

### 지금 (내 컴퓨터에서 도는 도구)

- 저작권법 제30조 **사적이용을 위한 복제** — 개인적으로 이용하거나 가정 및 이에 준하는 한정된 범위 안에서 이용하는 경우 복제할 수 있다
- 친구가 자기 컴퓨터에서, 자기가 쓰려고 받는 것 → 이 조항의 취지 안에 있다
- 도구를 만든 사람(나)은 서비스를 제공하는 게 아니라 **소스코드를 준 것**이다

⚠️ 단, 사적이용이어도 **불법으로 공유된 것인 줄 알면서 받으면** 이 예외가 적용되지 않는다.

### 웹에 배포하면 (서비스 제공)

성격이 근본적으로 바뀐다:

- 복제 행위를 **내 서버가** 한다. 친구가 아니라
- 나는 **온라인서비스제공자(OSP)**가 된다
- 사적이용 예외는 "개인적/가정에 준하는 범위"인데, **서버가 남을 위해 복제해주는 건 그 범위 밖**으로 볼 여지가 크다

한국 판례가 특히 무겁다. 대법원 전원합의체는 **불법 영상에 "링크만" 걸어둔 사이트 운영자도 저작권 침해 방조로 처벌할 수 있다**고 판시했다. 기준은 ① 영리 목적 ② 지속적 게시. 링크만 걸어도 그런데, **직접 다운로드해주는 서비스**는 훨씬 무겁다.

관련 조항:
- **저작권법 제136조** 벌칙 — 2026년 8월 11일부터 **7년 이하 징역 또는 1억원 이하 벌금**으로 상향 (기존 5년/5천만원)
- **저작권법 제104조** 특수한 유형의 OSP 의무 — 권리자 요청 시 차단 등 기술적 조치 의무, 안 하면 **3천만원 이하 과태료**

### 해외 흐름도 나빠지고 있다

미국에서는 **Yout v. RIAA** 소송에서 법원이 스트림 리핑이 DMCA의 기술적 보호조치 우회 금지에 걸린다는 취지로 판단했다. 2020년 RIAA가 youtube-dl을 GitHub에서 내리게 한 사건도 있었다(여론 반발로 복구되긴 했다).

### 그리고 이건 어느 쪽이든 위반이다

유튜브·인스타그램·틱톡 **이용약관은 다운로드를 명시적으로 금지**한다. 약관 위반 자체는 형사처벌 사안이 아니라 계정 정지·서비스 차단 같은 민사/계약 문제지만, 웹 서비스로 하면 **차단 대상이 내 서버**가 된다.

### 🔴 사실 더 중요한 것 — 배포와 무관하게 이미 봐야 할 문제

친구는 이걸 **영상편집 소스**로 쓴다. 즉 남의 영상을 받아서 **자기 결과물에 넣는다.** 이건 웹 배포와 상관없이 이미 존재하는 위험이고, 오히려 이쪽이 더 현실적으로 문제가 될 수 있다:

- 받는 것(사적이용)과 **그걸 편집해서 올리는 것(공중송신)은 완전히 별개 문제**다
- 유튜브·인스타에 올리면 Content ID에 걸리거나 저작권 신고를 받을 수 있다
- 인용(제28조)으로 정당화되려면 출처 표시, 주종관계(내 창작이 주), 필요최소한 등 요건이 있다

친구가 받은 영상을 **어디에 어떻게 쓰는지** 한 번 확인해보는 게 좋겠다. 참고용으로만 보는 거라면 문제가 훨씬 작고, 결과물에 넣어 업로드한다면 그쪽을 먼저 정리해야 한다.

## 3. 실제로 더 불편하다

"URL만 치면 되니까 편하다"는 직관과 반대로, 웹으로 가면 지금 잘 되는 것들이 깨진다.

| 지금 되는 것 | 웹에서는 |
|---|---|
| 받으면 **바로 내 폴더에** 저장됨 | 서버에 저장 → **친구가 또 내려받아야 함** (다운로드 2번) |
| 📂 저장 폴더 열기 (Finder) | ❌ 불가능 — `open` 명령은 서버 컴퓨터를 연다 |
| 📁 저장 위치 바꾸기 (맥 폴더 선택창) | ❌ 불가능 — `osascript`는 서버에서 돈다 |
| 자막 `.txt`가 영상 옆에 저장 | ❌ 파일이 서버에 있으니 무의미 |
| 🎧 음성인식 (내 맥 CPU, 공짜) | 💸 서버 CPU 비용. 동시 사용 시 대기열 |
| 🛠️ 편집용 파일 만들기 | 💸 인코딩 = 서버에서 제일 비싼 작업 |
| 원본 화질 그대로 | 대용량 파일 왕복 → 트래픽 비용 |

코드 기준으로도 [app.py:446](../app.py#L446)(`open`), [app.py:457](../app.py#L457)(`osascript`), [app.py:18](../app.py#L18)(홈 폴더)이 전부 **맥에서 직접 도는 걸 전제로 짜여 있다.** 웹으로 옮기려면 이 기능들은 그냥 없애야 한다.

거기다 서버 비용: 저장공간 + 트래픽 + 음성인식/인코딩 CPU. 친구 한 명 쓰자고 매달 돈이 나간다.

## 그럼 어떻게 하면 더 편해지나

"웹에 올리면 편할 것 같다"는 생각의 진짜 이유는 아마 **설치와 업데이트가 번거로워서**일 것이다. 그건 웹 배포 없이도 해결된다:

1. **업데이트는 이미 자동이다** — `실행.command`가 실행할 때마다 최신 코드를 받아온다. 내가 고치면 친구는 그냥 다시 켜기만 하면 된다
2. **아직 안 한 것 중 편해지는 것들**
   - 앱 아이콘 만들어서 독(Dock)에 넣기 — 더블클릭조차 안 하게
   - 맥 로그인 시 자동 실행
   - 실행할 때 검은 창을 숨기기
3. **정 원격이 필요하면** — 웹 배포 말고, 친구 맥에서 도는 걸 원격으로 보는 방식(화면 공유 등)이 법적으로도 기술적으로도 훨씬 안전하다

## 그래도 꼭 하고 싶다면 (최소 조건)

권하지는 않지만, 한다면 최소한 이건 지켜야 한다:

- **절대 공개하지 말 것** — 검색에 노출되거나 누구나 접속 가능하면 그 순간 "서비스"다
- **로그인 필수 + 친구 한 명만** — 계정을 늘리는 순간 성격이 바뀐다
- **광고·수익화 절대 금지** — 영리 목적은 방조범 판단의 핵심 기준이다
- **집 컴퓨터/집 회선에서 돌릴 것** — 클라우드는 IP 차단 때문에 어차피 잘 안 된다
- 서버 로그에 URL을 남기지 말 것, 받은 파일은 자동 삭제
- 호스팅 업체 약관도 확인 (대부분 이런 용도를 금지한다)

즉 **"공개 안 하고, 돈 안 벌고, 집에서 돌린다"**면 지금 방식과 실질적으로 같아지는데 — 그러면 굳이 웹으로 옮길 이유가 없다. 이게 이 검토의 결론이기도 하다.
